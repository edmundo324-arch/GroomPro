# Employee PIN and developer access

- PIN sign-in uses salted hashes and prefix checks. Imported/history-only records without usable PIN hashes are excluded from sign-in and collision checks. No PIN or verification metadata is fabricated for those records.
- Owners (ADMIN) can reveal or remove an employee PIN through the shared employee editor. Owners/managers retain existing reset authority. Blank new-PIN input preserves the current PIN. Removal disables PIN sign-in and ends that employee's sessions without deleting the employee or history.
- Existing hashes cannot be decrypted. A successful sign-in or authorized PIN reset stores an encrypted copy when GROOMPRO_PIN_VAULT_KEY is configured. Until then, reveal explains that the employee's PIN must be reset or successfully used once. PIN values never enter audit records.
- GROOMPRO_PIN_VAULT_KEY must be a private 64-character hexadecimal server secret. Back it up outside GitHub; changing or losing it prevents reading existing encrypted PINs. Local backup: C:/Users/Edmun/Documents/Codex/private-groompro/pin-vault-key.txt. Configure the secret separately on GoDaddy before using owner PIN viewing there. Sign-in hashing remains independent of this key.
- The explicit DEVELOPER role alone grants cross-business authority. Tenant Admins and Managers cannot grant that role, alter Developer credentials, or change Developer permissions. Settings > Subscription exposes Developer access controls only to Developers. Developers can suspend/restore a business, change employee access/PINs, and grant Developer authority, with an audit reason. This is manual access management, not payment-provider billing automation.
- Developer suspensions apply to internal protected application requests and sign-in. Employee history and customer data are retained. Public integration credentials are separate and are not revoked by these controls.
- At the owner’s request, the deployment bootstrap converts all existing development Admin accounts to Developer once, recording each change in the audit ledger. A database-wide migration marker prevents repeat conversion. An empty installation also records completion before any tenant is set up, so Admins created later remain tenant Admins. Existing PINs and employee records are preserved. No secrets are published.
